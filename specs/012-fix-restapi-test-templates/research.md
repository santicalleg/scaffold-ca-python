# Research: Fix RestAPI Entry Point Test Templates

**Feature**: `012-fix-restapi-test-templates` | **Date**: 2026-04-10

---

## Q1 — What is the correct import path for `create_app` in generated test templates?

**Decision**: Import from `{{ project.python_package }}.application.app`  
**Rationale**: `app.py.jinja2` defines both `create_app` and `start_server` inside `application/app.py`. The `server.py` template is a thin `__main__` wrapper that imports and calls `start_server` — it does not re-export `create_app`. Confirmed by reading `server.py.jinja2`:
```jinja
from {{ project.python_package }}.application.app import start_server
if __name__ == "__main__":
    start_server()
```
The existing `test_exception_handler.py.jinja2` already uses the correct import path and is the authoritative pattern.  
**Alternatives considered**: Re-exporting `create_app` from `server.py.jinja2` — rejected because it would couple the thin wrapper to the factory pattern unnecessarily.

## Q2 — What is the root cause of the duplicate content in `test_rest_controller.py.jinja2`?

**Decision**: The template contains two full blocks of content — an original block and a second block appended from an earlier merge. Only the second, more complete block (with a proper `TestClient` docstring and corrected assertions) should remain.  
**Rationale**: Inspecting the template reveals: line 1–31 is the first block (imports from `server`, assertions with hardcoded `"status": "app is online"`); lines 33–65 is the second block (imports from `server`, docstring comment, relaxed assertion `response.json().get("status") is not None`). Both import from `server` — both are wrong. The replacement must be a single clean block importing from `application.app`.  
**Decision for replacement**: Write one unified block that:
- Imports `create_app` from `{{ project.python_package }}.application.app`
- Tests `GET /v1/health` → 200 and a non-null status key
- Includes DI-override comment pattern
- Uses `starlette.testclient.TestClient` (consistent with other test templates)

## Q3 — What should `schemas.py.jinja2` contain?

**Decision**: A Pydantic v2 `BaseModel` placeholder `ExampleResponse` plus optional route-based response stubs when swagger routes are present.  
**Rationale**: 
- Pydantic v2 is the project standard (pyproject.toml: `pydantic>=2.0`; constitution §IV: "Pydantic v2 domain models")
- Without routes: emit `class ExampleResponse(BaseModel): status: str = "ok"` — a named, importable model that `test_schemas.py.jinja2` can reference
- With routes: emit one response model per route (named from path + method)
- The `routes` context variable is already available in `ctx_dict` passed to all restapi templates
**Alternatives considered**: Using TypedDict instead of BaseModel — rejected; Pydantic v2 is standard.

## Q4 — What should `test_schemas.py.jinja2` contain?

**Decision**: A test that imports `ExampleResponse` from the rendered `schemas` module and asserts it is a valid Pydantic model with the expected field.  
**Rationale**: `test_entry_point_restapi_test_schemas_template_has_example_response` CLI test already asserts `"ExampleResponse" in rendered_output`, so the name is fixed. The test should:
```python
from {{ project.python_package }}.infrastructure.entry_points.api.v1.schemas import ExampleResponse

def test_example_response_is_valid_schema() -> None:
    resp = ExampleResponse()
    assert resp.status == "ok"
```
**Alternatives considered**: Asserting only that the class is importable — too weak; asserting specific field values is better coverage.

## Q5 — What should `router.py.jinja2` contain, and should it be generated by `gep`?

**Decision**: `router.py.jinja2` exists as a supplemental template for CLI template-test coverage (`test_restapi_router_has_async_def`). It is **not** added to `_build_operations` — it is a reference file that documents the router pattern.  
**Rationale**: The `rest_controller.py.jinja2` already contains the `APIRouter` and `async def` route handlers. Adding a separate `router.py` to generated output would create a naming conflict. The failing CLI test `test_restapi_router_has_async_def` only validates the template renders to a file with `async def` — it does not require the file to be generated by `gep`.  
**Content**: A standalone APIRouter module with `async def` health endpoint — matches pattern of `rest_controller.py.jinja2` but stripped to the bare router without exception handler wiring.

## Q6 — Where in `_build_operations` should `schemas.py` and `test_schemas.py` be inserted?

**Decision**: Append `_src("schemas.py.jinja2", "schemas.py")` and `_test("test_schemas.py.jinja2", "test_schemas.py")` to the restapi operations list, after the existing `exception_handler.py` and before `test_*` entries.  
**Rationale**: The `_src` and `_test` helpers already handle `src_dir` / `test_dir` resolution — using them keeps the change minimal. Placement after `exception_handler.py` is natural (same directory level). The dry-run tree will list them alphabetically regardless of insertion order.

---

## Q7 — Should the two stale `test_restapi_main_has_*` CLI tests be deleted or updated?

**Decision**: **Delete** both tests from `tests/templates/test_entry_point_templates.py`.  
**Rationale**: Feature 011 deletes `main.py` when `gep --type restapi` runs. There is no `main.py.jinja2` in the restapi templates directory. These tests reference `entry_point/restapi/main.py.jinja2` which does not exist, so they will always raise `FileNotFoundError`. Creating a stub `main.py.jinja2` just to satisfy the tests would be misleading — it would imply `main.py` is still generated for restapi, contradicting feature 011's intent. Deletion is the correct remediation (confirmed by FR-006).  
**Alternatives considered**: Adding a tombstone `main.py.jinja2` — rejected; dead template would confuse future developers.
